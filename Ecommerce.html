Ecommerce API

solo project

A layered ecommerce backend covering the full loop — catalog, cart, checkout, and admin product management — built as a clean separation between API, application, domain, and infrastructure layers.

situation

On an earlier ecommerce project, business logic, validation, and database code ended up tangled inside the same controllers, so a small change in one place risked silently breaking something unrelated elsewhere.

task

Rebuild the same kind of system, but structured so a change to one layer couldn't quietly break another.

action

To stop persistence and business logic from bleeding into each other, I split the solution into five projects — Api, Application, Core, Infrastructure, Shared — so Infrastructure has no dependency on the API layer and Application never references EF Core directly; the database can change without touching a controller. To stop inconsistent error handling across endpoints, every request runs through FluentValidation first, and services return a result object instead of throwing exceptions for expected failures like "product not found" — so every controller handles errors the same way instead of each catching different exception types.

result

Cart, checkout, and admin product management all share the same validation and error-response pattern, and a daily Hangfire job on a separate SQL Server store emails members about new products without touching the main request path.

Architecture notes

  • JWT bearer auth with ASP.NET Identity, refresh tokens, email confirmation, and password reset built in.
  • Result-based response pattern used consistently across services and controllers, rather than exceptions for expected failures.
  • FluentValidation on every request, Mapster for DTO mapping.
  • Hangfire (separate SQL Server store) runs the scheduled product notifications and exposes a protected dashboard.
  • Serilog structured logging throughout the request pipeline.
