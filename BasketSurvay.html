Survey Basket

solo project

A polling API for creating, publishing, voting on, and analyzing surveys — with permissioned roles, scheduled email notifications, and production concerns like rate limiting and health checks built in from the start.

situation

Two members hitting submit on the same question at the same moment is a race condition a simple voting endpoint doesn't handle, and a public-facing poll API with no rate limiting is an easy target for spam votes.

task

Build a voting API that stays correct under concurrent access and can't be trivially spammed.

action

To stop simultaneous votes from racing each other, I put a concurrency limiter directly on the voting endpoint, restricted to the Member role, so competing requests queue instead of both writing at once; fixed-window rate limiting elsewhere in the API caps requests per IP and per user. Since results — by response, by day, by question — get read far more often than polls get created, I put a hybrid cache in front of those reads instead of hitting SQL Server on every results view.

result

The API serves poll results under repeated concurrent read/write load without corrupting vote counts, and a daily Hangfire job emails members automatically when a poll they can vote on goes live.

Architecture notes

  • JWT auth on top of ASP.NET Identity, with email confirmation and password reset flows.
  • API versioning through an X-api-Version header — the poll "current" endpoint has two live implementations side by side.
  • Hangfire on its own SQL Server store runs the recurring new-poll notification job.
  • FluentValidation, Mapster, and Serilog round out the request pipeline; documentation served through Scalar/OpenAPI in development.
